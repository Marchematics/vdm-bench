# Reproducing the leaderboards from code (and the three defects that found)

The leaderboards are generated by `run_reference.py`. Everything below was produced by running
that script from a clean checkout, *not* by reusing stored prediction files — which is how the
first two defects were noticed.

## What to run

```bash
# 100k SIFT: three tasks, fast (~2 min on 16 cores)
python run_reference.py --dataset sift --only analytics --full \
    --data-root /path/to/data --workloads workloads

# 10M SIFT: analytics only, and --full is mandatory for the ana-vec rows
python run_reference.py --dataset sift10m --only analytics --full \
    --data-root /path/to/data --workloads workloads
```

`--full` builds the index-backed submissions (a 10,000-cell IVF plus an HNSW per submission);
without it the writer only emits the trivial baselines. That is documented in the README, but it
was not, and a reviewer following the old README would have regenerated a leaderboard *missing*
the headline row — see defect 1.

## Defect 1 — the README dropped `--full`

Documented command lacked `--full`, so a regenerated 10M leaderboard contained only
`exact-oracle`, `uniform-sampling`, `ivf-plan`. Fixed in the README with the runtime and an
explicit warning that `--full` is a correctness requirement.

## Defect 2 — the ablation silently became the method (the serious one)

`ana-vec-sampling` is the ablation that carries the paper's causal claim: *same planner, same
cost, plain sampling instead of the stratified plan*. After the plan-selection refactor it was
selected as `range_plan or ("stratified" if n >= 2_000_000 else "two-phase")`, so with
`n_probe_lists=0` and `n >= 2_000_000` it fell through to the **stratified** plan. A full 10M
regeneration produced

| submission | range mean rel. err |
|---|---|
| `ana-vec` | 0.01636 |
| `ana-vec-sampling` | 0.01636 |

i.e. numerically identical, which would have looked like "the ablation shows the estimator change
does nothing". Plan selection now honours `n_probe_lists == 0` first. The 100k pair reproduces
exactly after the fix:

| submission | range err | p95 | coverage | join recall | cost |
|---|---|---|---|---|---|
| `ana-vec` | 0.013201 | 0.039434 | 1.000 | 0.99990 | 1.497e7 |
| `ana-vec-sampling` | 0.119493 | 0.642677 | 1.000 | 0.99990 | 1.441e7 |

A third, smaller defect fell out of the same read: the uniform plan's budget below 2M was set to
`wl["n"]` (a full scan) rather than the residual sample size, which would have made the 100k
ablation cost 7x more than the method it is supposed to match.

## Defect 3 — the 10M row depended on the reader's core count

Re-running 10M gave `0.01636` where the recorded run gave `0.01616`. The cause is that
FAISS k-means parallelises the distance reduction, so the centroids differ in the last bits
between thread counts (24 vs 32 here), which moves the estimator by ~1% relative. A benchmark's
headline row cannot depend on how many cores the reader has, so the builder now pins
`faiss.omp_set_num_threads(VDMBENCH_BUILD_THREADS)` (default 8) for the duration of the index
build and restores the previous setting afterwards.

Consequence to keep in mind when comparing runs: the *index-backed* analytics rows are
reproducible for a fixed `VDMBENCH_BUILD_THREADS`, and the sampling-based rows are reproducible
exactly (fixed seeds, no float reduction over threads). Numbers quoted from different thread
settings can differ in the third significant figure.

## Timing (16 cores, `joysuch`, shared host)

| run | wall clock |
|---|---|
| 100k SIFT, `--only analytics --full` | ~2 min |
| 10M SIFT, `--only analytics --full` | 25-45 min (two HNSW builds on 10M dominate; the host was shared and heavily loaded) |
