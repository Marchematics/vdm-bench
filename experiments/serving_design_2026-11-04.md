# Serving task: why the rows were missing, and how the task became discriminating

Date: 2026-11-04. All numbers below are **our re-measurement** of the shipped reference
submissions under the published workload (`run_reference.py --only serving`, SIFT, CPU-only,
held-out arrival traces). Provenance marker: 【本工作·同设置】 = our fair re-measure under
identical settings. No number here is a paper's own reported number.

## 1. Why the serving section of `leaderboard.md` was empty

There was **no traceback**. Running `python run_reference.py --only serving --full` on the
experiment host succeeds (it was re-run to confirm) and writes six correct serving rows — into
`leaderboard_sift.md`. The failure was a silent workflow bug with two parts:

1. `run_reference.py` wrote only `leaderboard_<dataset>.md`. The canonical `leaderboard.md`
   was hand-merged from those per-task files, so it was never regenerated by the script that
   the README says generates it.
2. Every `--only <task>` run rewrote `leaderboard_<dataset>.md` with *only that task's*
   sections. Commit `74fb663` (quality rewrite) removed the analytics/quality/serving rows
   from `leaderboard.md` during such a merge; `ef005b7` and `bdf44f1` restored analytics, and
   the serving rows were simply never put back. Subsequent `--only analytics` runs kept
   clobbering `leaderboard_sift.md`, which is exactly how the rows kept disappearing.

**Fix.** `run_reference.py` now has `merge_leaderboard()`: it parses the existing markdown and
replaces *only* the `## <task>` sections present in the current run, leaving every other
section byte-identical. A SIFT run writes both `leaderboard_sift.md` and the canonical
`leaderboard.md`. Running `--only serving` can therefore no longer empty the analytics section,
and `--only analytics` can no longer empty the serving section. The analytics and quality rows
in `leaderboard.md` were verified byte-identical after the serving merge.

## 2. Why the old serving task was saturated

The old workload swept `rhos = 0.70, 1.00, 1.15` only — near/below capacity. There the
only binding constraint is service order, so `serving-edf` (deadline order) and
`serving-vecslo` (deadline order + per-tenant effort quota) both scored 0.978 / worst 0.935,
identical to each other and to the effort oracle: the quota had nothing to allocate because no
tenant was ever capacity-starved. A task where every competent submission ties cannot separate
methods.

## 3. Redesign (workload generator + evaluator)

All changes are confined to the serving workload/evaluator and the serving baselines.

* **Load sweep includes overload.** `rhos = 0.70, 1.00, 1.15, 1.60, 2.00, 2.50, 3.00`
  (`SERVING_DEFAULT_RHOS`). 3 sub-capacity + 4 overload regimes. Reported metrics:
  `slo_pass` (mean), `slo_pass_worst` (worst regime = 3.0x), `slo_pass_overload` (mean over
  rho >= 1.6), `tenant_pass_worst` (worst tenant in the worst regime), p95/p99 latency over
  *served* queries, recall-SLO rate, goodput, `served_frac`.
* **Mixed hard/soft contract set** (published in `serving_meta.json` and shipped per query as
  `deadline` / `recall_req`): eight (L ms, R) classes —
  `hot-loose-cheap (140, 0.65)`, `tight-expensive (6, 0.99)`, `tight-high (9, 0.95)`,
  `tight-medium (7, 0.85)`, `medium-high (25, 0.95)`, `medium-low (30, 0.80)`,
  `loose-expensive (160, 0.99)`, `tight-low (5, 0.70)`. 30% of every tenant's queries are
  *hard*: deadline x0.6 and recall at a probe budget is the recall at half that budget, so
  they need 2x probes. The `tight-expensive` tenant's hard queries are infeasible at any
  effort (6.24 ms service against a 3.6 ms deadline); the correct action is to shed them.
* **Held-out trace kept.** `arrival` (pilot, visible) and `arrival_eval` (held-out, scoring),
  deterministic seeds. A submission returns a *policy*; it may be load-blind `(T, nq)` or
  load-indexed `(R, T, nq)` (the regime is public; the trace realisation is not).
* **Policy interface** accepts `efforts`, `priority` (higher = served first), `admission`
  (shed queries fail), and `reservation` (opt into per-tenant core partitions). All four were
  already accepted by the evaluator except `reservation`, whose simulator existed but was not
  wired in; it is now wired (`eval_serving` -> `_simulate_partitioned`).
* **Noisy difficulty signal.** `score = hard + N(0, 0.6)` (was a perfect detector of `hard`),
  so `serving-signal` is an honest imperfect-signal baseline instead of a copy of the oracle.

## 5. What now discriminates, and by how much

The separating column is **`slo_pass_worst`** (the 3.0x-overload regime), corroborated by
`slo_pass_overload` and the p99 tail:

* `serving-static` / `serving-adaptive` / `serving-signal` collapse under overload:
  worst-regime 0.014 / 0.027 / 0.022, overload mean 0.019 / 0.048 / 0.032. Effort-only methods
  with FCFS ordering are capacity-blind once offered load exceeds capacity.
* `serving-edf` is clearly below `serving-vecslo` on the discriminating column:
  **0.184 vs 0.553 (3.0x)**; overload mean **0.330 vs 0.650 (2.0x)**; p99 **2159 ms vs 317 ms
  (6.8x)**; goodput 2649 vs 4229 qps. The mechanism is visible in the per-tenant data: EDF
  orders by deadline and therefore spends capacity on the tight-deadline *expensive* contracts
  (including hard queries that cannot make their deadline) while starving the loose-deadline
  cheap hot tenant. The per-tenant effort/admission quota rations by *cost*, not by deadline.
* `serving-oracle` is above both: 0.587 worst regime, 0.690 overload mean, 0.801 mean, 101 ms
  p99 — it can shed the hard class of a tenant independently of its soft class.

## 6. Honest caveats

* `tenant_pass_worst` is 0 for **every** policy at 3.0x overload. EDF starves the
  loose-deadline tenants; the quota and the oracle concentrate service on cheap contracts
  (`served_frac` 0.84 / 0.81). This is reported rather than hidden: the task now discriminates
  on aggregate compliance and the latency tail, and tenant isolation under 3x overload remains
  an open axis (the evaluator accepts per-tenant `reservation` for future work).
* The oracle's margin over the quota submission is real but modest (0.587 vs 0.553 worst
  regime) because the quota's subset/admission search already captures most of the cost-aware
  behaviour; the larger gap is quota vs EDF.
* `recall_slo` is computed over all queries from their effort level and does not fold in
  admission; read it next to `served_frac`.
* One run per submission (deterministic seeds); no seed variance is claimed. The workload
  and traces are bit-identical across hosts (verified by array-content hash). The
  quota/oracle *search* is deterministic given the environment, but floating-point
  tie-breaks can move one coordinate-ascent step on a different numpy build (observed:
  oracle rho=1.15 gave 0.919 on the experiment host and 0.909 on a laptop). The
  leaderboard numbers are the experiment-host run.

## 7. Reproduce

The reference run is CPU-only but the quota/oracle searches are not cheap: `run_reference.py
--only serving` takes roughly 10-20 minutes single-threaded on a loaded host (the six
submissions are tuned on the pilot traces and scored on the held-out traces).

```bash
python prepare.py --data-root /path/to/data --dataset sift --only serving
python run_reference.py --data-root /path/to/data --dataset sift --only serving
python evaluate.py --task serving --data-root /path/to/data --workloads workloads \
    --predictions submissions/serving-vecslo/predictions.json
```
